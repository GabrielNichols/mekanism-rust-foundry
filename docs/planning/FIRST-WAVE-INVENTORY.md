# First-wave effective inventory crosswalk

This crosswalk connects existing laboratory evidence and first-wave candidates to the nominal [inventory](INVENTORY.md), [requirements](requirements.json), and [scenario designs](functional-scenarios.json). The planning files contain 117 capability families, 253 behavioral requirements, and 22 scenario designs. Their counters describe that planning baseline. The rows below describe individual observations and proposed slices. Use the existing family and requirement IDs for all coverage claims.

## Status contract

Each row tracks five independent facts. `partial` limits a positive observation to the described behavior. `design` means a scenario outline exists and still requires an executable binding.

| Field | Meaning |
| --- | --- |
| Mapped | A stable object or candidate is linked to an existing family or roadmap item. Record where the identifier came from. |
| Runtime | A local run demonstrated the particular object, registration, or behavior. A resource inside the archive and an aggregate loader count have their own evidence classes. |
| Scenario | A committed executable case, a harness-owned treatment, or a planning design exists. Identify which. |
| Executed | The linked runtime evidence identifies an actual completed attempt, its result, and the exercised portion. Read-only archive inspection and simulations retain their own scope. |
| Reviewed and sealed | The selected expected reference has a reviewed outcome, declared limits, locked provenance, and a verified seal. A run trace hash or trace-seal check alone leaves this field open. |

Qualification is a separate decision on a declared scope. Every listed behavioral slice remains unqualified for gameplay porting. Keep failed attempts and negative controls alongside passing evidence.

## Next effective export

Use the Core dedicated profile first. Emit a deterministic, namespace-resolved snapshot after the selected data packs and configuration have applied. Include active module IDs and artifact hashes, registry kinds/IDs and candidate tags, recipe IDs/types and resolved input/output forms, effective scoped config values, menu type IDs and slot schemas where a real client opens the menu, and a resource manifest with normalized paths and hashes. Keep stateful examples attached to their topology and evidence IDs. Expose absent or unresolved values explicitly, including optional module or integration requirements. Capture a second identical baseline and a deliberate missing/changed-entry control. Compare any accelerated profile against the serial 20 ticks/s semantic baseline before accepting its result.

Selection of a reviewed reference needs a scoped outcome and negative control, immutable artifact/profile/configuration hashes, a seal check, and a review record. Keep raw archives, generated configs, screenshots, traces and logs private. Share selected IDs, counts, digests, and bounded outcomes in the public tree. Move a row forward only when its linked evidence supports the particular state being changed.
